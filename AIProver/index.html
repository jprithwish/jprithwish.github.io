TL;DR
  1. The AIProver proof auto-formalization agent with an evolving harness. AIProver post-trains an open-weight LLM and simultaneously evolves its harness. Verifiers for completeness, type- and semantic correctness return a fine-grained reward and certificate, so reinforcement learning and HarnessEvolve learn from partial success. Per round, HarnessEvolve adapts the harness control flow to the model, then RL post-trains the model within it.
  2. LoCoBench, a research-level benchmark for proof auto-formalization. 58.9k instances (18.8k NL–Lean, 40.1k NL–Mizar) in algebraic structures; foundations, logic & complexity; and number theory, with 771 validation instances from Mizar theorems with the longest proofs and a bounded-arithmetic textbook: NL theorem–proof pairs with no Lean formalizations online to retrieve or imitate.
  3. State-of-the-art proof auto-formalization results. Against 39 systems: as a standalone agent built from Leanstral-1.5, AIProver lifts pass@4 semantic correctness from 15.7% to 36.7%, beating the best open-weight system OpenGauss (21.5%) and Aristotle (18.4%). In conjunction with coding agents, AIProver+Claude Code reaches 79.8% vs. 41.9% for Claude Code alone, and AIProver+Codex 62.4% vs. 34.1%, at lower cost than Numina-Lean-Agent and OpenGauss in the same role.

01 · Problem

Research mathematics needs an affordable, autonomous auto-formalizer

AI agents for mathematics are making rapid progress, with headline results such as the resolution of the Navier–Stokes conjecture and the complete formalization of Fermat’s last theorem. Key to this success is auto-formalization, the translation of natural language (NL) theorems and proofs into formal language (FL) counterparts. Research mathematics involves long chains of interdependent definitions, lemmas and proofs often absent from libraries such as Mathlib, so recent work wraps the LLM in a harness: a stateful multi-turn loop with Lean and search tools in which the agent iterates until the proof checks. Despite this progress, these agentic systems share five limitations.

  1. CostClaude’s FLT formalization took eleven days and six billion output tokens, resources at frontier rates beyond typical academic budgets.
  2. Human-in-the-loop dependenceMathematicians supplied Fermat’s FL target statements and stayed involved; Gauss ran on an expert-built, iteratively refined harness; Meta’s AutoformBot calls human involvement essential.
  3. Jagged intelligenceFrontier models excel at many tasks yet falter on unfamiliar ones: strong local proof repair but poor definitions and interfaces, and no model proves over 20% of ArXivLean’s recent research theorems.
  4. Semantic driftLean checks the FL proof against the FL theorem, not the NL one, so compiled code may prove the wrong theorem or silently patch a flawed NL proof step.
  5. Lack of accessibilityHeadline results often rest on non-public models, so the auto-formalization and proof synthesis (AFPS) process cannot be cross-checked.

The goal

An affordable, autonomous AI agent for semantically correct and faithful proof auto-formalization of research-level mathematics, serving standalone as an open-source platform that makes research-level formalization accessible to all, and in conjunction with frontier agents as a Lean specialist pushing their accuracy–cost frontier.
(a) FaithfulProduce a full Lean counterpart preserving each theorem’s meaning and proof’s reasoning.
(b) UnattendedRun without a mathematician in the loop.
(c) Open-weightUse an open-weight model via a model-agnostic training and harness recipe.
(d) A skillBe a sub-agent or skill of frontier agents, which will likely stay the most expensive models.

Four issues, four answers

Issue 1 · NL–FL semantic alignment

A decoder-only LLM is fine-tuned to maximize the next-token likelihood of a reference output, so it never learns that an NL theorem and its FL counterpart are the same mathematical object in two syntactic forms.

Semantic Alignment Model (SAM). The LLM itself internalizes the equivalence: a contrastive term aligns the NL and FL views in a shared semantic space.
Issue 2 · Fine-grained training signal

Most AFPS models are trained with RL on Lean’s binary verdict, which never compares the output with the NL input or the reference FL: a formalization that compiles but proves the wrong theorem counts as success.

Reward ladder with certificates. Four verifier checks return a graded reward and a diagnostic certificate, so RL and harness search learn from partial success.
Issue 3 · Research-level training data

Gold NL–Lean theorem–proof pairs barely exist: ShadowBench (178) and ArXivLean (41) are evaluation sets. Mizar holds decades of verified research mathematics, but in neither NL nor Lean.

LoCoBench. 58.9k instances from Mathlib, CSLib, the Mizar library and a textbook, with a 771-instance validation split that has no Lean formalization online.
Issue 4 · AFPS-tailored harness

Harnesses such as LeanMarathon and Numina-Lean-Agent retain the control flow of Claude Code and Codex, built for software engineering; it is suboptimal for Lean proving and for open-weight models, and hand-tailoring takes months.

HarnessEvolve. A certificate-driven evolutionary search over the whole harness control flow re-tailors the harness to the updated model.

The task proof auto-formalization, under four properties

The input is a self-contained NL passage: a theorem, possibly in several parts, with the definitions and assumptions it relies on, and its proof, possibly through intermediate lemmas. The goal is an equivalent Lean pair, subject to four properties. Lean mechanically certifies (a) and (b); (c) and (d) compare the formalization with its NL source, which is undecidable and so requires a judge.

MNL · natural language
TNLtheorem: definitions, assumptions and claims
PNLproof: steps and intermediate lemmas
→proof auto-formalization
M̂FL · Lean 4
T̂FLdefinitions and the theorem as a type
P̂FLtactics and auxiliary lemmas as a term of that type
  • Lean certifies(a) Type-correctnessLean’s kernel accepts the file: every definition and tactic step resolves and the proof term type-checks.
  • Lean certifies(b) CompletenessThe proof uses no placeholder such as sorry, admit or an empty by block, and no axioms beyond Lean’s standard ones.
  • Judge(c) Semantic correctnessThe formal theorem states exactly TNL under the same definitions, neither adding assumptions nor dropping conditions.
  • Judge(d) Proof faithfulnessThe formal proof follows the proof strategy of PNL, including its intermediate lemmas, without new assumptions.

02 · Approach

AIProver post-trains the model and evolves the harness together

Definition · agents and harnessesAn agent A = ⟨M, H⟩ pairs an LLM M with a harness H, the software layer that executes the actions M proposes in a stateful environment. It governs the agent’s context, tools, memory and control flow: the system prompt, how tool calls are handled, what state persists across turns, and when it stops. AIProver optimizes the full agent, post-training M and evolving H.

Bootstrap first, then alternate: HarnessEvolve re-tailors the harness to the current model, and Agentic RLSF post-trains the model inside the new harness, so each update builds on the other’s latest gain. Harness and model use disjoint training subsets, and every round is gated on held-out fitness.

Fig. 1 · WalkthroughThe co-evolution loop: bootstrap, then interleave HarnessEvolve and Agentic RLSF for K gated rounds
  1. StartLeanstral-1.5 (119B-A6B) as M₀, inside a seed harness H₀ adapted from Mistral’s Vibe with Lean LSP tools.
  2. Bootstrap the harnessHarnessEvolve evolves H₀ into H₁ under the frozen base model.
  3. Bootstrap the modelSAM fine-tuning turns M₀ into M₁ on the labelled NL–Lean pairs of LoCoBench-Train.
  4. Round i: evolveWith Mᵢ frozen, HarnessEvolve re-tailors the harness to the updated model.
  5. Round i: post-trainWith Hᵢ₊₁ frozen, Agentic RLSF post-trains Mᵢ into Mᵢ₊₁ inside it.
  6. Gate and repeatThe new pair is kept only if its held-out fitness improves, else rolled back. K rounds.
  7. Click a step to jump to it.

Harness and model are updated in alternation, never at once, so each update sees the other’s latest state.

03 · Components

One graded reward and one certificate drive both the model’s and the harness’s search

A candidate formalization is scored with four checks, ordered so that each presupposes the preceding one. Every check returns a value and a certificate from the verifier. The reward is the per-rollout signal for RLSF and, averaged over tasks, a harness’s fitness; the certificate is what HarnessEvolve’s mutator reads as feedback.

(1) Type-correctness · TCLean accepts the file: every definition and tactic step resolves and the kernel type-checks the proof term.Certificate: Lean’s diagnostics verbatim, each error’s position, the failing tactic with its open goals, or the expected versus actual type.
(2) Completeness · CPEvery goal is closed without a placeholder, and no axioms beyond Lean’s standard ones: a check for sorry and an audit with #print axioms that fails on native_decide or an agent-introduced axiom.Certificate: the placeholder’s position or the violating axiom.
(3) Semantic correctness · SCThe formal theorem states the same theorem as the gold one, tested as logical equivalence with an extended BEq+ that proves each direction in Lean. One direction alone gives vSC = 0.5; both give 1.Certificate: both verdicts and, on a miss, their asymmetry.
(4) Length fidelity · LFHow close the proof’s length is to the gold one, with 60 characters of slack. A far shorter proof relies on heavy automation like grind; a longer one meanders; both are less human-readable.Certificate: the length ratio.

The reward ladder (Table 1 of the paper). A matched theorem outweighs completeness, as a flawless proof of the wrong theorem is not useful; a solved instance loses at most 0.10 for length. The certificate states the verdict and r, then concatenates the checks’ certificates in ladder order, so the first failing check is the first to fix.

HarnessEvolve certificate-driven evolutionary search

HarnessEvolve evolves the current harness while the model stays frozen. A harness is a finite but arbitrarily long program, so the search is over a countably infinite space for the harness maximizing the fitness on the training set. Each round grows a search memory by one node through four stages.

Search memory · a tree that keeps every verdict
  • A node stores a harness with its fitness, its per-instance rewards and certificates, and its verdict: accepted or rejected.
  • An edge stores the source diff between parent and child and their fitness difference.
  • Every evaluated harness is kept, so the mutator learns which changes raised fitness from the accepted ones and which to avoid from the rejected ones, as conflict-driven clause learning in SAT solvers learns a clause from every refuted assignment.
  1. Parent selectionAn upper-confidence rule, as in UCB1 and UCT, picks an accepted node, exploiting high-fitness nodes while exploring rarely expanded ones; its exploration weight rises with each consecutive non-accepting round.
  2. MutationA frontier coding agent rewrites the parent into a child. The tree, with every node’s fitness and certificates, shows which edits raised fitness and which did not, so it avoids refuted hypotheses and changes the control flow where the certificates show recurring failures.
  3. Rollout and fitnessThe child harness runs with the frozen model on every training instance, k times each to average out stochasticity; the fitness is the mean reward, and the certificates are stored in memory.
  4. AcceptanceThe child is accepted if its fitness beats the best so far, else rejected, and is added to the memory in either case. After R rounds, the best accepted harness goes to RLSF.
Model · cold start

Semantic Alignment Model (SAM)

A decoder-only LLM fine-tuned to represent MNL and MFL as the same mathematical object, which language modeling alone does not induce. A contrastive term is optimized jointly with the language-modeling loss, aligning the two in an NL/FL shared semantic space. Two forward passes yield two views: the hidden state at a reserved [PRED] token after the NL text, where generation of the Lean begins, and the final state of the Lean text alone, so the views align on meaning alone.

Effect. The cosine of matched NL–FL pairs rises from 0.11 to 0.75, and RLSF mostly keeps it (0.64). SAM remains a generative LLM, but conditions generation on semantic meaning rather than structural form alone.

Model · post-training

Agentic RLSF

Reinforcement learning via symbolic feedback for multi-turn agents. An episode is one run of the agent inside the frozen new harness: the model attempts auto-formalization by reasoning, calling tools and observing their results, turn after turn. Only the Lean file it finally writes is rewarded, by sound symbolic tools (the Lean kernel and BEq+) instead of unreliable learned reward models. Optimized with GRPO; the objective applies only to tokens the model generated.

Why the ladder matters. Outcome supervision makes the fine-grained reward essential: under a binary verification reward most groups of rollouts have no spread and yield no gradient.

Harness · seed

Seed harness and what evolved

The seed harness adapts Mistral’s Vibe with the lean-lsp tools. Relative to it, the evolved harness adds middleware hooks around the agent loop (a search gate, budget notices and post-agent verification), answer snapshots, a finalize step, a task contract with the four-rung grading order, and a compile-and-repair loop.

Effect. Evolving the harness at a fixed model lifts type-correctness from 57.6% to 84.4%; the harness alone mostly fixes compilation, which motivates post-training.

04 · Benchmark

LoCoBench: 58.9k research-level instances, 771 of them with no Lean formalization online

A benchmark for proof auto-formalization of research-level mathematics in three fields: algebraic structures (ring and group theory), foundations, logic & complexity (set theory, logic, computability, model theory, bounded arithmetic) and number theory. No existing research-level dataset offers NL theorem–proof pairs at this scale: ShadowBench has 178 examples and ArXivLean no proofs.

SourcesFrom Mathlib and CSLib, 10.2k, 5.9k and 2.7k Lean theorem+proof pairs for the three fields, each a standalone, type-checked .lean file after dependency analysis. From the Mizar Mathematical Library, 18.3k, 8.0k and 13.8k pairs, one .miz file per theorem. And the 71 pairs of a research-level bounded-arithmetic textbook, from its author.
InformalizationLLMs informalize (FL-to-NL) far more accurately than they formalize. Each file is informalized by a coding agent (Claude Code with Opus 4.8) in a feedback loop with CriticLeanGPT, an NL–FL faithfulness judge, revising until it passes.
Train / Val splitVal is out of distribution: its Mizar theorems come from MML papers disjoint from Train, and its textbook domain appears in neither library. Mathlib+CSLib instances go to Train because their Lean is public. Val is the 100 longest-proof Mizar theorems per domain plus the 71 textbook theorems; its proofs are about 8× ProofNet’s.

As a standalone agent
  1. Open-weight models are far from research-level AFPS without a Lean-tailored harness. Every open-weight AFPS or foundation model stays below 3.9% TC+SC. AIProver raises this nearly tenfold, to 36.7%.
  2. It outperforms frontier LLMs and agents. GPT-5.6-Sol (25.2%), Aristotle (18.4%) and Codex (34.1%); only Claude Code (41.9%) is higher.
  3. The gain is from post-training and the evolved harness. From the same Leanstral-1.5 base, it outperforms OpenGauss on each field (36.7% vs. 21.5%), and its 67.0% on number theory is above Codex (62.0%) and Claude Code (57.0%).
As a skill for frontier coding agents
  1. AIProver lifts both hosts more than prior harnesses. Claude Code goes from 41.9% to 79.8% (vs. 72.5% with Numina-Lean-Agent and 54.3% with OpenGauss), and Codex from 34.1% to 62.4% (vs. 44.5% and 41.9%).
  2. The gain comes from AIProver rather than the host. It adds 28.3% to Codex and 37.9% to Claude Code, whereas Numina-Lean-Agent adds 10.4% and 30.6% and OpenGauss 7.8% and 12.4%. The weaker host gains almost three times more from AIProver than from either prior agent.

06 · Cost

07 · As a skill

A Lean specialist that frontier coding agents call

AIProver is packaged as a skill that a tool-calling coding agent loads; the experiments use Claude Code and Codex as hosts. The skill gives the host a small command-line interface and a fixed protocol; the host never reads AIProver’s trajectories, only its returned Lean files and their checks.

AIProver writes Lean and searches for proofsOne call is a complete agentic session of the post-trained model inside the evolved harness, up to 200 turns with Lean and the lean-lsp tools, run on local GPUs, so a job of k parallel samples costs the host nothing but a wait.
The host does what needs judgementIt reads the NL passage, plans, judges semantic correctness (c) and proof faithfulness (d) of every returned file, fixes statements, decomposes, and weaves the pieces together. It does not search for proofs itself, and it does not stop until all four properties hold.
  1. Preflight. Check the environment: Lean and Mathlib, the completeness checker, the model endpoint, and one live rollout.
  2. Blueprint. The host lists the definitions, the theorem parts with their exact hypotheses, and the proof’s intermediate lemmas, and resolves ambiguities such as the number type or indexing convention.
  3. Submit. It submits the whole problem to AIProver with k = 4 samples, plus a statement-only job on long inputs, and waits.
  4. Judge. It judges every sample that passes (a) and (b), best first, and accepts the first that also passes (c) and (d).
  5. Decompose. Otherwise it fixes the statement and decomposes: it freezes a skeleton with the definitions and every lemma and theorem part as a statement with sorry, submits one job per open piece with the frozen context and that piece’s NL fragment, weaves the returned proof bodies into the skeleton, and resubmits a failing piece with a one-line hint or splits it further along the NL proof.
  6. Final gate. Rerun the type-correctness and completeness check on the exact final file, and the judge protocol once more.
